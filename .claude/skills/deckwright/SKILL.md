# Deckwright

One JSON file is a game. The browser client, the match relay and the LitNode ruleset all run
**the same rules code**, so what players see is what any node would replay.

```
NFT collection ─snapshot─► collection/cards.json ─import─► games/<id>.game.json
games/<id>.game.json ─┬─ web   ─► web/ (static site: engine, data, art) ─► Vercel or any static host
                      ├─ relay ─► per-match WebSocket relay (dev now, LitNode gauntlet later)
                      └─ title ─► rulesets/<id>.js (LitNode, later)
```

**Running commands.**
- **In a game project** (made by `deckwright create`): run `npx deckwright <cmd>`, or the npm scripts in its `package.json` (`npm run sim`, `npm run web`, `npm run dev` and so on).
- **In the Deckwright repo itself:** run `pnpm deckwright <cmd>`.

| In a game project | Role |
|---|---|
| `games/<id>.game.json` | The game: cards, deck, elements, champion mapping, rules |
| `collection/cards.json` | Output of `deckwright snapshot` (gitignored; re-run it to refresh) |
| `web/` | The site. `engine/`, `data/` and `assets/art/` are **generated by `deckwright web`**; `index.html`, `app.js`, `app.css` and `lib/` (wallet, holdings, RPC) are yours to restyle |
| `vercel.json` | Static hosting and the CSP |
| `gauntlet.json` | LitNode hosting config, for later |

The SDK's own source (`src/core` rules, `src/client` sessions, `src/litnode`, `src/tools`) is in the Deckwright repo, or in `node_modules/deckwright/src` inside a game project.

## Workflow

1. **Start**: `npx github:strodanodev/deckwright create my-tcg` (or `npx deckwright create` once it is on npm). This scaffolds the project and builds a playable site with neutral champions.
2. **Bring a collection** (any ERC-721):
   - Read it: `npx deckwright snapshot <address> --chain liteforge --out collection`. For other chains use `--rpc <url>` and, if it has one, `--explorer <blockscout url>`.
   - Then `npx deckwright import collection/cards.json --id my-tcg --out games`.
   - ERC-6699 `coreStats` become champion stats. Without them, champions are neutral. Pass `--registry <addr>` if the agents live in a separate registry.
3. **Edit** the cards, deck, elements, champion mapping and rules. Field reference: [references/game-config.md](references/game-config.md).
4. **Balance**: `npx deckwright sim games/my-tcg.game.json --matches 300`. It must show `replay mismatches 0`. Aim for 45–55% first-player wins and about 0% `hit maxTicks`.
5. **Compatibility**: `npx deckwright title games/my-tcg.game.json`. It must end `ok`. Add `--litnode <dir>` to run LitNode's real conformance suite.
6. **Site**:
   - Build it: `npx deckwright web games/my-tcg.game.json --collection collection/cards.json`.
   - Serve it: `npx deckwright dev`, then open `http://127.0.0.1:4173`. Use `127.0.0.1`, not `localhost`.
7. **Multiplayer (dev)**:
   - Run `TCG_DEV=1 TCG_GAME=games/my-tcg.game.json npx deckwright relay`.
   - Open the site twice, with `?relay=ws://127.0.0.1:7830&name=alice` and `&name=bob`.
   - One relay process serves one match.
8. **Deploy**: `vercel deploy --prod` from the project root. The site is static and served from `web/`, with no build step on the host. Rebuild with `deckwright web` and commit before deploying.

## Rules that keep matches replayable

- **The rules core is pure and integer-only.**
  - It must not use `Math.random`, `Date`, timers, `fetch`, `WebSocket`, storage, `crypto.`, `process.env` or `import()`.
  - Those words must not appear in core source even in strings. LitNode's purity lint scans the bundle.
  - Randomness comes only from `seededRandom(seed)`.
- **Any rules or card change is a new `litnode.rulesetId` version** (`.v2`). Rebuild the site and the ruleset.
- **Two players, one integer frame per log entry.**
  - The acting side sends the action; the other side sends 0.
  - Illegal or garbage frames are no-ops, never throws.
  - `maxTicks` bounds a match.
- **Champions.**
  - A champion's ERC-6699 CoreStats arrive as `ctx.agents[player].stats`; with no champion, every stat is 0.
  - The client, the relay and the ruleset must all hydrate the same way.
  - The site maps snapshot stats `str/agi/res/int` to `strength/agility/resilience/intelligence`.
- **Open information.** v1 has no hidden hands. Commit-reveal, or ZK proofs on top of it, would be a new ruleset version.
- **Safe UI.** Card and collection names come from on-chain data. Set them with `textContent` only, never `innerHTML`. The CSP allows no inline script, so page logic lives in `app.js`.
- **Art is served locally.** The CSP's `img-src` is `'self'`, so `snapshot` downloads art. Remote art URLs are dropped by `web`.
- **Rights.** The Rapture demo content (art, names) is © LitVM Games and not covered by the code license (see `NOTICE`). Don't ship it in a builder's game without permission.

## Extending (in the Deckwright repo)

- **New effect op**:
  1. Add it to the `Effect` union in `src/core/types.ts`.
  2. Handle it in `resolve()` in `src/core/rules.ts`.
  3. Accept it in `validateGame()`.
  4. List its targets in `legalActions()`.
  5. Teach the bot's score in `src/core/bot.ts`.
  6. Describe it in `describe()` in `web/app.js`.
  7. Re-run `pnpm sim`, `pnpm title`, `pnpm web` and `pnpm test`.
- **Card mapping for a collection**:
  - In `src/tools/import-collection.ts`, Rapture Kinds use the `KIND` table; other collections get stat-power quintiles.
  - Elements form a cycle; Rapture's four keep `RAPTURE_BEATS`.
  - Traits: `snapshot --kind-trait` and `--element-trait` pick which metadata traits are read.
- **Release**:
  - `pnpm build` writes `dist/` (the `npx deckwright` CLI); `npm pack` makes a tarball for testing.
  - `package.json` stays `"private": true` until the owners decide to publish.
- **LitNode**: deferred. See [references/litnode.md](references/litnode.md) for hosting (`gauntlet.json`), registration and known gaps.
- **Where it came from**: [references/pipeline.md](references/pipeline.md) maps the LitVM Games pipeline (Rapture Studio, PackShop, ERC-6699, LitNode).
